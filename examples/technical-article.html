Designing a reading layer that survives real websites

A technical walkthrough focused on isolation, target detection, reflow, and conservative article discovery.

Original demo text · code and table included

An in-page reading tool lives in an unusually hostile environment. It is injected into documents it does not control, after stylesheets it did not author, around markup that may be semantic, generic, malformed, or generated by a framework. The first engineering requirement is therefore not visual polish but isolation: the interface must keep working when the host page has aggressive global selectors.

Shadow DOM is a practical boundary for that interface. It prevents most host CSS from leaking into the controls and allows the reading surface to define its own typography. The page content that is copied into the lens can then be sanitized so that structural meaning survives while classes, inline styles, event handlers, and unsafe interactive elements are removed.

Target detection should be narrow before it becomes clever

The fastest reliable target is a semantic reading block such as a paragraph, list item, blockquote, preformatted block, table cell, or heading. A short minimum text length filters out labels and tiny fragments. Only after that direct lookup fails should the tool consider generic containers.

function findTarget(start) {
  const direct = start.closest('p, li, blockquote, pre, h1, h2, h3');
  if (direct && direct.textContent.trim().length >= 24) return direct;

  // Conservative fallback for generic containers.
  return findNearbyReadableContainer(start);
}

The fallback must be conservative because generic containers are everywhere. Navigation rows, button groups, card wrappers, and account panels may all contain enough text to look interesting. Excluding headers, navigation, toolbars, menus, and footers before scoring generic containers prevents many false positives.

Article discovery has a different confidence threshold

A paragraph target only needs to be useful locally. Article mode is broader, so the threshold should be higher. Semantic roots such as article, main, and [role="main"] are strong signals. Without them, the fallback container should have multiple readable blocks, substantial text, plausible dimensions, and a link ratio that does not resemble a navigation surface.

Single paragraphStrongWeak
Multiple text blocksOptionalStrong
High link ratioSuspiciousReject
Semantic <article>Context onlyStrong

The user-interface rule follows directly from that confidence model: a visible action should be available. If the tool cannot identify a plausible article root, the Article button should disappear rather than remain visible and fail after a click. Hiding unavailable scope is less frustrating than asking users to understand the heuristics behind the feature.

Reflow is more important than geometric scale

A reading surface should change the font size and let the text lay itself out again. CSS transforms can make pixels larger, but they do not create a better line measure. Real reflow produces shorter lines at larger sizes and preserves normal selection, copying, and text navigation.

function setZoom(scale) {
  content.style.fontSize = `${16 * scale}px`;
  content.style.lineHeight = scale >= 1.7 ? '1.62' : '1.56';
}

That simple operation works because the lens itself has a constrained width. The combination of larger type, bounded measure, and stable line height changes reading ergonomics without changing the surrounding page. It is a local typographic adaptation rather than a page-scale transformation.

Interaction stability matters as much as detection

A small activator is useful only if the pointer can reach it. Moving from a paragraph toward the activator may cross child elements, links, or inline spans. A naive pointerout handler can interpret those transitions as leaving the target and start a hide timer. The implementation therefore has to distinguish leaving the readable block from merely moving inside it.

This is the sort of bug that synthetic unit tests rarely expose. A live demo page with links, code, headings, and long paragraphs is useful because it turns pointer behavior into something a person can feel immediately. If VL flickers or vanishes while the pointer is moving toward it, the interaction is broken even if every internal function returns the expected value.
